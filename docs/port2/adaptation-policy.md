# Adaptation policy — normative for S3–S9

**Status:** governing document. Assembled from the six area readers in
`docs/port2/adaptation/01-types.md` … `06-collections.md`, all of which were read in full.
Where this document and an area document disagree, **this document wins**; where this document is
silent, the area document is the detail record.

**Scope of authority.** §1 is the rule. §2 is the work list. §3 is the waiver ledger. §4 is the
pre-registration of every deliberate deviation from the fork. §5 re-scores the open decisions.
§6 collects everything that is not yet established.

**Evidence tags used throughout:** `MEASURED` (code was executed and its output pasted in the area
document), `READ_FROM_SOURCE` (read at a named file:line), `INFERRED` (reasoned, not executed).
Every `INFERRED` row must be probed before its owning stage starts — §2.3 lists them.

## 1. The policy

> **Uncertainty meaning comes from the fork. Everything else comes from USE 7.5.0.
> Where the two collide, keep the uncertainty behaviour but express it the 7.5.0 way.**

This was decided by the user. It is not open for debate; a stage author's job is to apply it.

### 1.1 The worked example

| expression | fork (MEASURED, 2021 jars) | plain USE 7.5.0 (MEASURED, `use-core/target/classes`) | **the port must answer** |
|---|---|---|---|
| `Set{UReal(2,0.5), 1, 2.5}` | `Set(UReal)` | compile error `probe:1:4: Undefined operation 'UReal'.` | **`Set(UReal)`** |
| `Set{UReal(2,0.5), 1, 2.5}->sum()` | `UReal` / `UReal(5.5, 0.5)` | compile error | **`UReal`** |
| `Set{1, 2.5}` *(control)* | `Set(Real)` | `Set(Real)` | `Set(Real)` — both agree |
| `1/0` | `Undefined : OclVoid` | `null : OclVoid` | **`null : OclVoid`** |

Reproduced end-to-end by three independent readers (01 §4.1, 04 §3.1, 06 §1.1/§1.2).

### 1.2 How to apply the rule to a new case — four questions, in order

1. **Is the behaviour under dispute uncertainty meaning?** If a U-type, a U-value, an uncertainty
   operation or an uncertainty-lifted result is what makes the answer differ, the answer comes from
   the fork. `Set(UReal)` is uncertainty meaning. `Set(Real)` is not.
2. **Is it a defect?** If the fork's answer violates a contract it does not intend
   (`equals` reflexivity, `Comparable` antisymmetry, `equals`/`hashCode` consistency, a declared
   type that its own value does not conform to, an unguarded array index), **B7 applies: fix it and
   pre-register the fix in §4**. B7 is a *policy*, already decided; it is not a per-row licence to
   improvise.
3. **Is it merely older?** If the fork's version is 2015 upstream and 7.5.0 has moved on
   (`sortedBy`'s `OrderedSet` branch, `import java.util.*`, `visitObjOp`→`visitInstanceOp`,
   `Op_number_pow`/`Op_number_sqrt`, `qualifiedName()`, `modelQualifiedType`), **7.5.0 wins,
   unconditionally.** Taking the fork's file wholesale is how ten years of upstream drift gets
   silently deleted. **File-level copying from the fork is forbidden for every file marked "edit".**
4. **Does 7.5.0 already have a mechanism for it?** If so, use 7.5.0's mechanism rather than the
   fork's. `TypeFactory.buildInTypesMap` instead of grammar keywords; a semantic predicate on
   `IDENT` instead of an implicit token; two `return false;` roots inherited by six leaves instead
   of six edits; the named-operation path instead of a bespoke `identicalExpression` rule.

### 1.3 Three consequences the user has already accepted

* **B5** — the lattice falsifies 10 of the 12 assertions in upstream's untouched
  `TypeTest#testSupertype`. **One** written rule-3 waiver covers it (§3).
* **B6** — the port prints `null`; the 79 corpus entries expecting `Undefined` are normalised at
  comparison time by rule **N1**, never by reverting the port.
* **B7** — the 33 behaviour-changing ledger defects are FIXED and documented, not reproduced.
* **B2** — `SBoolean` is ported in full (39 operations), independently corroborated by a live
  registry dump: 39 anonymous `SBoolean` enum constants (03 §1.2).

## 7. Checklist for a stage author

1. Read §1. Apply the four questions in order. If the answer is not obvious, the case is in §2.
2. Find your rows in §2 by stage. Do every `⚑` row's probe **before** writing code.
3. Every behavioural difference from the fork that you produce must already be in §4. If it is not,
   either it is a porting error or §4 needs a new row — decide explicitly, do not proceed.
4. If an upstream test fails, the default conclusion is that your change is wrong. The **only**
   sanctioned waiver is **W-01** (§3). Adding a second requires the same evidence shape as §3.2.
5. Never copy a fork file over a 7.5.0 file. Never diff without `tr -d '\r'`.
6. Paste `git diff --name-status` over `*/src/test/*` in your stage report (rule 3 has no automatic
   signal until B3's profile runs).
